# Changelog

## 0.0.23

- `bonefish`: complex level 1 and `gemv` (R3). `blas::{axpy, scal, copy, swap, dot, dotc, nrm2, asum, iamax, gemv}` and the matching `Scope` methods now take `Complex<f32>` and `Complex<f64>` as well as `f32` and `f64`, through a new sealed trait `BlasElement` (its associated `Real` type is the result type of `nrm2` and `asum`, which are real even for complex input; the bound on those functions changed from `Scalar` to `BlasElement`, which every previously accepted type satisfies). `dot` is the **unconjugated** product (BLAS `dotu`); the new `dotc` conjugates the first vector (for real data the two are the same). `iamax` follows oneMKL's rule, the largest `|re| + |im|` (not the modulus), first index on ties; a test whose data separates the two rules checks it. `bonefish-sys`: 20 `bf_{c,z}{axpy,scal,copy,swap,dotu,dotc,nrm2,asum,iamax,gemv}_async` (`shim/complex.cpp`), all under the oneMKL lock and in the lock-counter test, each moving it by exactly one.
- Tests (`tests/complex_blas.rs`, 8): each op against a naive reference with strides, `Complex<f32>` within float tolerance, the `dotu`/`dotc` split, the `iamax` rule, `gemv` for all three ops, the scoped chain, and refusals as for real data. The real-data tests are unchanged and pass.
- **Known problem, not fixed (ROADMAP R12):** on Windows, running these tests on parallel threads crashed about 1 run in 10 inside oneMKL (a delay-load failure in `mkl_sycl_blas.6.dll` followed by a jump to an unmapped address), only when different routines ran for the first time concurrently. The test file warms up every op serially first (0 of 100 crashes vs 11 of 100 without, same binary); the mechanism is not shown. The library does not warm up for you.
- Not verified: any GPU, Linux locally, other oneMKL releases.
- Version number is a placeholder for the PM (stacks after 0.0.22).

## 0.0.22

- `bonefish`: complex `gemm` (R3b/R3). `blas::gemm`, `Scope::gemm` and `Scope::gemm_after` now accept `Complex<f32>` and `Complex<f64>` as well as `f32` and `f64`, through a new sealed trait `GemmElement` (the real types forward to the existing `Scalar` methods, so nothing changes for existing callers; the bound on those three functions changed from `Scalar` to `GemmElement`, which every previously accepted type satisfies). `Transpose::ConjTrans` is honoured for complex data (it is the same as `Trans` for real data). `bonefish-sys`: `bf_cgemm`, `bf_zgemm`, `bf_cgemm_async`, `bf_zgemm_async` (new `shim/complex.cpp`; all under the oneMKL lock and in the lock-counter test, each moving it by exactly one). Complex `alpha` and `beta` cross the C boundary **by pointer to two reals**, never by value: passing a C++ `std::complex` through `extern "C"` by value is not something to rely on.
- Tests (`tests/complex_gemm.rs`): all nine `(op(A), op(B))` pairs of `{No, Trans, ConjTrans}` for `Complex<f64>` against a naive reference (max error < 1e-12, 5x4x3, `alpha = 0.5 - 2i`, `beta = 1 + i`), `Complex<f32>` within 1e-4, the scoped form against the blocking one, and the same refusals as real `gemm`. Controls: `ConjTrans` must differ from `Trans` on data with imaginary parts, and swapping `alpha`'s real and imaginary parts must change the answer. **Mutation-checked on both paths:** swapping `alpha`'s halves in the blocking hand-off fails the double-precision and control tests (max error 40.25); swapping `beta`'s halves in the async hand-off fails the scoped test; both files restored byte-identical.
- Not verified: any GPU, Linux locally, other oneMKL releases. Complex level 1 (`axpy`, `scal`, `copy`, `swap`, `dotu`/`dotc`, `nrm2`, `asum`, `iamax`) and complex `gemv` are not in this release.
- Version number is a placeholder for the PM (stacks after 0.0.21).

## 0.0.21

- Docs only, a correction to 0.0.20. 0.0.20 presented oneMKL's padded default real-domain DFT layout as a finding and listed "whether Intel documents it" as unchecked. It is documented: Intel's oneMKL DPC++ Developer Reference 2026.0 (Document ID 772045, dated 4/28/2026), page "Configuring data layouts", says descriptors are "default-configured for unbatched, in-place transforms" and that "for real descriptors, minimal padding is used in forward domain" (section "Configuring strides in forward and backward domains"), and that this "leads to some data padding to be used in forward domain if unit strides are used" (section "Data layout requirements"). So it is a footgun, not a defect, and it was never in `docs/INTEL-REPORT-DRAFT.md`. Replaced (not annotated) in ROADMAP R11, the 0.0.20 entry below and the `src/rdft.rs` module docs. Limits of the check: the page's stride formulas are images that were not in the text I could read, so the exact default formula is not quoted (the measured row stride of 8 for a last dimension of 6 is consistent with it, but is a measurement); the page does not state an out-of-place default; the oneAPI specification page returned HTTP 404 and was not read. No code change.
- Version number is a placeholder for the PM (stacks after 0.0.20).

## 0.0.20

- `bonefish`: `RealDft<T>` (R3b), the real-domain DFT: `RealDft::new(&queue, &lengths, fwd_scale, bwd_scale)`, `forward` (real array to half spectrum) and `backward` (half spectrum to real array), `f32` and `f64`, 1-D to N-D, **out of place only**, blocking. Both sides are dense and row-major; the complex side's last dimension has `n_last/2 + 1` entries. `real_len()` / `complex_len()` report the sizes. Refusals before the device is touched: no dimensions, a zero length, a buffer shorter than the plan, a buffer from another queue. Like `Dft`, neither `Send` nor `Sync` (compile_fail `E0277` pins with a `Queue` control). `bonefish-sys`: `bf_dftr_new`, `bf_dftr_free`, `bf_dftr_compute`, `bf_dftr_compute_async` (new `shim/dftr.cpp`; all four take the oneMKL lock and are in the lock-counter test, each moving it by exactly one). The zero/negative-length guard is now one shared helper (`bf::check_dft_lengths`) used by the complex and the real paths.
- **Documented, and easy to trip on: oneMKL's DEFAULT real-domain layout is the in-place one, with padded rows, even for an out-of-place transform** (ROADMAP R11, which cites Intel's 'Configuring data layouts' page; a footgun, not a defect, so it is not in the Intel report draft). A delta at element (1, 0) of a dense 4 x 6 real array gave an all-zero spectrum because the default input is read with a row stride of 8, not 6; the 2-D comparison against a naive DFT was off by 8.08. The shim therefore sets `FWD_STRIDES` / `BWD_STRIDES` explicitly. After that, 1-D (lengths 1, 2, 3, 4, 5, 7, 8, 12, 16), 2-D (4x6, 5x3, 3x8), 3-D (2x3x4, 3x2x5), single precision, scales, backward and the 2-D round trip all match the naive DFT, and a deliberately transposed reference is detected (negative control).
- Not verified: any GPU, Linux locally, other oneMKL releases; in-place real transforms (not offered); the scoped async real DFT (not built).
- Version number is a placeholder for the PM (stacks after 0.0.19).

## 0.0.19

- `bonefish`: device-time profiling and a launch floor (R5b, `docs/FUEL-INTEL-GPU-DESIGN.md`). `Queue::new_profiling(kind)` and `Queue::with_device_profiling(&info)` make a queue whose events can report device time (profiling can only be chosen at creation; `Queue::is_profiling()`); `Event::device_time()` waits for the operation and returns `DeviceTime { start_ns, end_ns }` (SYCL `command_start` / `command_end`, nanoseconds on the device's own clock, so only differences are meaningful); on a queue made without profiling it is `Error::InvalidArgument`, never a zero. `Scope::noop()` submits an empty kernel (chained like any other operation): its device time is the launch floor. `bonefish-sys`: `bf_queue_new_ex(kind, device_index, flags)`, `bf_event_profiling`, `bf_noop_async`.
- Measured (Windows laptop, OpenCL CPU device, oneAPI 2026.1): empty kernel about 70 us, 1024^2 f32 `gemm` about 4 to 5 ms (median of 7). **Not verified:** that a GPU queue supports profiling, what its timestamps mean, and the profiling overhead.
- Tests (`tests/profiling.rs`): a `gemm` reports `0 < start < end` and its result is right; the same call on a non-profiling queue is a named error, with the identical call on a profiling queue as the control; the empty kernel is at least 10 times faster than a real `gemm`; consecutive operations' device timestamps do not overlap. **That last test has no teeth against the shim's submission chain** (it passes 25 of 25 with the chain off, because an in-order queue orders native kernels); it only checks the timestamps are consistent, and its comment says so.
- ROADMAP R8 gains a third unexplained stall: the new test binary hit a 120 s timeout once in 40 runs and was clean in 400 more (240 whole-binary, 160 single-test); the tests now have a 60 s watchdog that names the test.

## 0.0.17

- **Fix: a queue freed right after a wait could terminate the process.** `bf_queue_free` now retires the queue and destroys it only after a grace period (default 2 s, after a `wait_and_throw`), instead of at once. Found as an intermittent Linux CI abort (`async_shim` SIGABRT: SYCL's default async handler printed 'forced asynchronous failure' and called terminate; 5 of 180 looped runs on main). Reproduced on Windows with 4 threads each looping {new queue, failing host task, one wait, free}: destroying at once killed 25 of 25 processes, one thread 0 of 25. Cause: a wait can return before the runtime posts a task's error (R3c); if the queue is gone when the error arrives it goes to the default handler, which terminates. Compared under that probe: destroy at once 0 of 20 survive; wait then destroy at once 0 of 20 (so waiting alone does not help); never destroy 59 of 60; grace 50 ms 20 of 20; grace 2 s 40 of 40.
- `BONEFISH_UNSAFE_QUEUE_GRACE_MS` sets the grace period for A/B runs (0 reproduces the abort). Retired queues are leaked at process exit on purpose. New test file `bonefish-sys/tests/queue_drop.rs`. ROADMAP R10 has the numbers and the list of what is NOT shown (the real bound of the posting delay; a real failing kernel; Linux in a loop until measured; one unexplained residual in 'never destroy' mode).
- Cost: a program that frees many queues keeps each alive 2 s longer (memory and device handles, not data).
- Version number is a placeholder for the PM (stacks after 0.0.16; PR #18 uses the same placeholder and needs the next number after this one).

## 0.0.15

- `bonefish::blas`: blocking safe wrappers for level 1 and `gemv`, `f32` and `f64` (R3): `axpy`, `scal`, `copy`, `swap`, `dot`, `nrm2`, `asum`, `iamax` (zero-based, an error for `n = 0`) and `gemv`. Each is "submit on a `Queue::scope`, wait", so the bounds checks, the output-is-not-an-input refusal, the submission chain and the collection of asynchronous errors are the scope's, with one implementation of each. Scalar results (`dot`, `nrm2`, `asum`, `iamax`) are returned as values.
- Consequence, stated so nobody is surprised: these report an asynchronous device error the way `Queue::scope` does (collected at the wait, and rarely delivered by a later wait on the same queue, see `Queue::scope`), whereas the older blocking `blas::gemm`, `Dft::forward*` and `UsmBuffer::copy_from_slice`/`to_vec` call the shim's blocking entry points, which wait with `wait()`. Measured for `bf_memcpy` (3 of 3 runs, `a_blocking_call_behind_a_failing_task_does_not_report_its_error`): a failing task submitted just before it is waited for, the call returns success, and the error stays in the queue's store until a later wait that collects it. The other blocking entry points share the same `wait()` but were not measured individually (ROADMAP R3d). Not changed in this release.
- Tests: `tests/blas_blocking.rs` (hand-computed answers for all nine in both precisions, strided `x`, transposed `gemv`; refusals: short buffer, zero increment, a buffer or queue mismatch, `iamax` of nothing; the refused calls leave their buffers untouched). CPU/OpenCL device only; GPU UNVERIFIED.

## 0.0.13

- `bonefish`: scoped non-blocking level 1 (`axpy`, `scal`, `copy`, `swap`, `dot`, `nrm2`, `asum`, `iamax`), `gemv` and DFT (`Scope::plan` binds a `Dft` with a shared borrow; `dft_forward`/`dft_backward`, in place and out of place) on `Scope`, for `f32` and `f64` (R3c step 3). Vector increments must be at least 1. Refusals before anything is submitted: a buffer too short for its extent, a zero increment, a result buffer that is empty, an output that is the same buffer as an input, a plan of the wrong placement, a plan or buffer from another queue. `i64` is now an `Element` (the index `iamax` writes).
- `bonefish-sys`: `bf_{s,d}{axpy,scal,copy,swap,dot,nrm2,asum,iamax,gemv}_async` and `bf_dft_compute_async` (each returns the event, takes a dependency array; only the submission is under the oneMKL lock), and the DFT plan handle now carries its queue's error store so an async DFT's errors are attributed to that queue.
- **Retraction (reaches `docs/ASYNC-DESIGN.md` 3.4/6 and the `Queue::scope` docs, replaced in this release): an in-order queue does not order oneMKL calls.** 0.0.11 and 0.0.12 said the scope's operations cannot overlap because the queue is in-order (a "soundness requirement" the SYCL specification supplies). That was never measured for oneMKL and is false on this build: on an `in_order` queue, `dot` submitted right after `axpy`/`copy`/`gemm` read the old data in 98 to 100 of 100 rounds (Windows, oneAPI 2026.1, CPU/OpenCL; standalone C++, three runs); 0 of 100 with the earlier event passed as a dependency; `scal`->`axpy`, `axpy`->`asum`/`nrm2`, `gemm`->`gemm`, `dot`->`axpy` were ordered. The only operation the 0.0.12 safe API exposed was `gemm`, and `gemm`->`gemm` was ordered, so no wrong result from 0.0.12 is known; the argument was wrong, and it would have broken with the next operation added.
- Fix: the shim chains every asynchronous submission to the queue's previous asynchronous event (`deps_chained`), so the order does not depend on which calls the library happens to order. With the chain on all eight measured pairs are right in every round; with it off the same binary reproduces the stale reads. `BONEFISH_UNSAFE_NO_ASYNC_CHAIN=1` (or `bf_test_set_async_chain(0)`) turns the chain off: a diagnostic for exactly that A/B and for retesting a newer oneMKL, not a feature. Safe-API end-to-end test `dot_straight_after_axpy_sees_the_axpy`: passes 5 of 5 with the chain, fails 5 of 5 without (10 instead of 70).
- Docs: `docs/INTEL-REPORT-DRAFT.md` finding 2 with the standalone reproducer `docs/intel-report/repro_order.cpp` (draft, **not sent**). `bonefish-sys/tests/mkl_lock.rs` classifies and counts the 19 new functions (mutation: submitting without the lock fails with "bf_saxpy_async moved the oneMKL lock counter by 0, not 1").
- Not measured: any GPU; Linux locally; other oneMKL releases; `iamax` and the DFT call without the chain; a failing kernel (as opposed to the forced host-task error) in the async level-1/DFT paths.
- Version number is a placeholder for the PM (stacks after 0.0.12).

## 0.0.12

- `bonefish`: the scoped non-blocking API (R3c step 2, `docs/ASYNC-DESIGN.md`). `Queue::scope(|s| ...)` gives a `Scope` on which `gemm`/`gemm_after` (f32, f64) return an `Event<'scope>` without waiting; buffers are bound once with `s.read(&buf)` / `s.write(&mut buf)` (a `Read`/`Write` handle holding a shared/exclusive borrow until the scope ends), and the scope waits for the queue on normal return, on error and on panic, then returns the first asynchronous error. Bounds are checked as in the blocking `gemm`; an output that is also an input of the same call is `InvalidArgument`; a buffer from another queue is `QueueMismatch` at binding. `Scope` is `Send` and `!Sync`. The blocking functions are unchanged.
- Pinned by tests: `compile_fail,E0502` (host read while bound for writing), `compile_fail,E0505` (drop while bound for reading), a compile_fail that an `Event` cannot leave the scope (the compiler's error is "lifetime may not live long enough" at the returned value), `compile_fail,E0277` for `Scope: Sync` with a `Send` control; `tests/scope.rs` (dependent chain, explicit event dependency, queue mismatch, aliasing, bounds, **a panic inside the scope still waits**: mutation-checked, with the wait disarmed that test fails 12 of 12 runs, and passes with it); an in-crate test that an asynchronous failure comes back from `scope` and is not reported twice.
- **Fix to 0.0.11 (shim): asynchronous errors are now kept per queue, not per thread.** 0.0.11 collected them in a per-thread list on the assumption that SYCL runs the async handler on the waiting thread; it does not promise that. Measured on Windows (oneAPI 2026.1, CPU) with four threads on four queues: 138 of 300 failures lost on failing queues (343 of 600 in another shape) and a clean queue once reported another queue's error. Now `bf_queue_new` gives each queue an error store its handler captures, event handles carry their queue's store, and each wait drains its own queue's. After the fix: 0 foreign errors in 9 runs, 0 of 150 lost single-threaded. Remaining, and not ours: with four threads active about 2 to 5 in 100 errors are not yet posted when the first wait returns; all 66 of 66 missed ones were reported by a later wait on the same queue. So `Ok` from `scope` is not proof the work succeeded; documented on `Queue::scope`. A failing kernel (as opposed to the forced host-task error) was not measured; GPU UNVERIFIED. Found when the Linux oneapi CI job failed once on the in-crate scope test (lost error, then passed on rerun).
- Not shown: that in-order matters for correctness on any device (the CPU device ran an out-of-order queue in order, ROADMAP R3c); any GPU. Level 1/`gemv` and `Dft` are still blocking-only.
- Version number is a placeholder for the PM (stacks after 0.0.11).

## 0.0.9

- **Finding: oneMKL is not host-thread-safe in the shipped build, contrary to the oneAPI specification.** With oneAPI 2026.1 on Windows (CPU/OpenCL device), concurrent first use of `gemm` from four threads crashes inside `mkl_sycl_blas.6.dll` (exception `0xC06D007F` or an access violation): 28 of 40 runs of a standalone C++ program with no bonefish code, and 15 of 15 fresh-process runs of the Rust threading tests. On Linux CI (oneAPI 2026.2, OpenCL CPU, ubuntu runner) the same tests hung. SYCL allocation under threads alone was fine (25 of 25).
- `bonefish-sys`: every oneMKL entry point in the shim (all BLAS, all DFT including plan creation and free) now takes one process-wide mutex. With it, the same Rust threading tests pass 15 of 15 (and 20 of 20 earlier) fresh-process runs, the same binary with `BONEFISH_UNSAFE_NO_MKL_LOCK=1` passes 0 of 15. That switch is a diagnostic only, for retesting a newer oneMKL. Cost: oneMKL calls from different threads take turns; SYCL allocation and copies still overlap.
- `bonefish`: `Queue` and `UsmBuffer<T>` are `Send + Sync` (`Rc` became `Arc`). The basis is the SYCL 2020 rule for SYCL calls plus **our lock** for oneMKL calls, not Intel's thread-safety claim. Unverified: any GPU, other oneMKL releases, Linux with 2026.1.
- `Dft` stays neither `Send` nor `Sync` (the oneAPI specification says class-based objects "may not be shared between concurrent host threads unless otherwise specified"), pinned by `compile_fail,E0277` doctests with `Queue` and `UsmBuffer` as the passing control.
- `bonefish-sys/tests/mkl_lock.rs` fails if a oneMKL call bypasses the lock. The shim exports `bf_mkl_lock_acquisitions` (a counter of entries into the lock path); every foreign function declared in `src/lib.rs` must be classified as oneMKL or not (an unclassified one fails the test, so a new function cannot slip through), each oneMKL function must move the counter by exactly one, and the non-oneMKL ones must leave it unchanged (the control). Checked by mutation: switching `nrm2` from `guard_mkl` to `guard` fails it with "bf_snrm2 moved the oneMKL lock counter by 0, not 1"; reverted.
- Docs: `docs/INTEL-REPORT-DRAFT.md` and the reproducer `docs/intel-report/repro.cpp`, a draft report for Intel with versions, numbers and what was not measured. **Not sent**; whether and where to send it is for CireSnave (board).
- OPEN (not explained, not attributed to load): one `safe_api` test process hung with the lock on (see ROADMAP R8).
- Tests (`tests/threads.rs`): a watchdog turns a hang into a named failure; each operation is run alone (allocation, copies, `gemm`, one DFT plan per thread) with a shared queue, at 1, 2 and 4 threads, plus the control of one queue per thread; the threading tests are serialised against each other. CPU/OpenCL device only; GPU UNVERIFIED.
