| R10 | **A queue freed right after a wait can terminate the process when the task's error is posted late.** Found as an intermittent Linux CI abort in `bonefish-sys --test async_shim` (SIGABRT, 'Default async_handler caught exceptions ... forced asynchronous failure', 'terminate called without an active exception'; 5 of 180 looped runs on main across Xeon 8370C and EPYC 7763; PR #18 run 41180305507 on an EPYC 9V74). Cause reproduced on Windows (oneAPI 2026.1, CPU device) with a probe: 4 threads each looping {new queue, failing host task, free the event, ONE wait, free the queue}: **25 of 25 processes died** with the queue destroyed at once, 0 of 25 with one thread. Mechanism (consistent with the R3c measurement that a wait can return before the error is posted): the error arrives at a queue that no longer exists, goes to SYCL's default handler, which terminates. Mitigations compared under that probe (processes surviving): destroy at once 0 of 20; wait_and_throw then destroy at once ('grace 0') 0 of 20; never destroy 59 of 60; grace 50 ms 20 of 20; **grace 2000 ms (the fix) 40 of 40**. So waiting before destroying is NOT enough; time is. **Fix (0.0.17):** `bf_queue_free` retires the queue and destroys it only after a grace period (default 2 s, after a `wait_and_throw`); retired queues are leaked at process exit on purpose. `BONEFISH_UNSAFE_QUEUE_GRACE_MS` overrides it for A/B runs. Regression test `bonefish-sys/tests/queue_drop.rs` (own file: an abort kills only that process). **Not shown:** the real upper bound of the posting delay (2 s is 40 times a 50 ms grace that survived 20 of 20 here, which is a margin, not a proof); that this exact test is clean on Linux in a loop (to be measured before merge); whether a REAL failing kernel or oneMKL call (as opposed to the forced throwing host task) is posted late the same way; the single residual failure seen once in 'never destroy' mode (1 of 60) is unexplained and not seen again in 40 more runs; a long-running program that frees many queues holds each for 2 s longer. The uncaptured Windows `async_shim` failure noted in R3c may have been this | review |
