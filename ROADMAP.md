Windows, standalone C++ (no bonefish code), 4 threads x 40 runs: cold 12 ok / 28 crashed (18 x 0xC06D007F in mkl_sycl_blas.6.dll, 6 access violations, 4 other); one global mutex around gemm 40/40 ok; one serial warm-up gemm on ONE queue first 40/40 ok (so the race is process-wide first-use initialisation, not per-queue); SYCL malloc/free only, shared or own queues, 25/25 ok; 1 thread 12/12 ok; 2 threads 2 of 12 crashed. Windows, Rust stack, same binary, fresh process each: WITH the shim lock 15/15 ok (20/20 earlier), WITHOUT it (BONEFISH_UNSAFE_NO_MKL_LOCK=1) 0/15 ok (11 x 0xC06D007F, 4 access violations). Not oversubscription (it happens with 2 threads, and stops with a lock or a warm-up). Mitigation shipped: one process-wide mutex in the shim around every oneMKL call, so thread-safety is ours by construction; `bonefish-sys/tests/mkl_lock.rs` fails if any oneMKL-calling shim function bypasses it (mutation-checked). | R3c | **Non-blocking operations and `Event`** (design: `docs/ASYNC-DESIGN.md`, PM ruling: scoped safe API over an unsafe C layer, in-order queues). **Step 1 done (shim, 0.0.11):** every shim queue is in-order and has an `async_handler`; `bf_sgemm_async`/`bf_dgemm_async` return a `sycl::event*` and take a dependency array; `bf_event_wait`/`bf_event_free`/`bf_queue_wait`; tests in `bonefish-sys/tests/async_shim.rs`. **Measured (Windows, oneAPI 2026.1, CPU/OpenCL; GPU UNVERIFIED):** (a) an asynchronous failure (a throwing host task) arrives as status 1 with its message through both `bf_event_wait` and `bf_queue_wait`, and is not reported twice **(single thread; with several threads see the correction below: the 0.0.11 per-thread error list lost about half of the errors and was replaced by a per-queue store in 0.0.12, and a missed error can still arrive from a later wait on its queue)**; with the `async_handler` removed the same test kills the process (SYCL's default handler prints the exception and the process exits, code 127), so the design note's worry in section 5 was real and the test has teeth. (b) **The dependent-chain test has NO teeth on this device:** with the `in_order` property removed an out-of-order queue still passed it 15 of 15, so only the `is_in_order()` property test pins in-order here; whether in-order matters for correctness on any device is not shown by this test. (c) The `mkl_lock` counter test now covers the two async functions (lock held for the submission only; the device work then runs unlocked, which is UNVERIFIED for thread-safety). **Step 2 done (0.0.12), with a FIX to step 1:** the 0.0.11 shim kept asynchronous errors in a per-thread list; measured with four threads that lost 138 of 300 errors and once reported a foreign one, so errors are now per queue (clean queues: 0 foreign errors in 9 runs); what remains is that the runtime can post an error just after a wait returned (about 2 to 5 in 100 with four threads active, 0 of 150 single-threaded; all 66 of 66 missed ones were reported by a later wait on the same queue).  the `bonefish` scoped API (`Queue::scope`, `Scope`, `Read`/`Write`, `Event<'scope>`, async `gemm`/`gemm_after`) with `compile_fail` pins for `E0502`, `E0505`, no escape and `Scope: !Sync`, and a wait-on-panic test that fails 12 of 12 when the wait is disarmed. **Next:** step 3, async `Dft::compute` and level 1/`gemv` (the shim has only async `gemm` so far). | in progress |

| R7 | **icpx default fast-math vs accuracy claims.** Measured (icpx 2026.1.0.20260617, Windows, CPU/OpenCL device, JIT; one kernel `out = expf(x)` at x = 3.0f, correct value 20.08553695678711): default flags give 20.08906364440918 (rel error 1.8e-4); `-ffp-model=precise` and `-fno-fast-math` each give 20.085536956787109; `-fsycl-fp32-prec-sqrt` changes nothing; `#pragma float_control` is ignored on this target; `sycl::exp(x)` is correct under the default flags. Any accuracy or perf claim for Intel (Fuel included) must state the flags and the math spelling: libm names (`expf`) under default flags are NOT comparable with CUDA or Vulkan results. `bonefish-sycl-emit` avoids it in source (every libm call becomes `sycl::`); a user compiling their own SYCL needs `-ffp-model=precise` (or `-fno-fast-math`). Not yet measured: other functions (only `exp` was run), Linux, any GPU (GPU math lowering may differ), `-fp-model=` spellings other than the two above. Left: sweep every unary op default-vs-precise vs `sycl::`, then repeat on a GPU | todo |
